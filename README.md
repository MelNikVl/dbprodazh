# АН PRO — аналитика продаж

Веб-приложение для анализа CRM-выгрузок за 2024–2026 годы. Основной вопрос — где снижаются продажи 2026 года относительно 2025. Исторический контекст, товарная детализация, клиентская база и план-факт собраны в одном интерфейсе на русском языке.

Код: [MelNikVl/dbprodazh](https://github.com/MelNikVl/dbprodazh). Локальный адрес — [localhost:8050](http://localhost:8050), адрес домашнего развёртывания — [192.168.0.15:8050](http://192.168.0.15:8050).

## Возможности

| Раздел           | Содержание                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| Где теряем       | Выручка, тоннаж, АКБ, план; потери по сетям, группам и SKU; вклад групп в изменение продаж     |
| Динамика продаж  | Помесячное сравнение 2024, 2025 и 2026 за одинаковый период                                    |
| Структура продаж | Доли каналов и сетей, изменение доли в процентных пунктах                                      |
| Товарные группы  | Переход от группы к SKU, сети и торговой точке; позиции со снижением продаж                    |
| Онлайн           | Сравнение онлайн-сетей, тепловая карта роста по группам                                        |
| Ключевые сети    | Продажи сетей и вклад товарных групп                                                           |
| Прочие клиенты   | Клиенты вне онлайн-канала и ключевых сетей; рост и потери                                      |
| Клиентская база  | Активные, новые, ушедшие и сохранённые точки за выбранные месяцы                               |
| SKU-матрица      | Ассортимент по сетям, добавленные и выбывшие позиции, детализация SKU                          |
| План продаж      | План-факт в тоннах, заложенный и исторический рост, выполнение, разрыв и оценка реалистичности |

В разделе **Качество данных** доступны источники, предупреждения импорта и покрытие по месяцам. В **Настройках** редактируются правила объединения клиентов, правила группировки SKU и пороги оценки.

Глобальные фильтры: период, деньги/тонны, канал, сеть, группа, регион, дистрибутор и сопоставимая база. Таблицы с кнопкой экспорта выгружаются в Excel. Кнопка «Отчёт PDF» создаёт готовый PDF с десятью разделами и выбранными фильтрами. Если браузер блокирует автоматическое скачивание, остаётся ссылка на готовый файл.

## Архитектура и хранение

- Интерфейс: React и TypeScript, графики Recharts, чтение и экспорт Excel — SheetJS.
- Excel разбирается в Web Worker браузера. Аналитические расчёты также выполняются в браузере.
- Сервер раздаёт готовое приложение и разрешённые исходные файлы. В Docker это один процесс Node.js; при разработке используется Vite.
- Данные отчёта и файлы, выбранные через интерфейс, находятся в памяти текущей страницы. После перезагрузки приложение заново читает серверные исходники; ручные загрузки нужно повторить.
- Правила и пороги сохраняются в `localStorage` текущего браузера. Между пользователями и устройствами они не синхронизируются.
- База данных не используется: в приложении нет общего редактирования записей, серверной истории импортов или сохранённых отчётов. Для резервной копии нужны исходные файлы и настройки, а не дамп БД.

Ручной импорт через интерфейс не загружает данные на сервер. Серверный каталог исходников подключается к контейнеру только для чтения. CRM-файлы, контрольные значения сверки, `.env` и локальные рабочие материалы не должны попадать в Git или Docker-образ.

## Источники и импорт

Автоматическая загрузка использует пять файлов с точными именами:

- `2024 год.xlsx`
- `2025 год.xlsx`
- `2026 год.xlsx`
- `план Август (4).xlsx`
- `план Сентябрь (6).xlsx`

Путь к каталогу задаёт `CRM_SAMPLE_DIR`. Если исходники недоступны, файлы можно выбрать в интерфейсе. Поддерживаются `.xlsx`, `.xls` и `.csv`; ожидается структура продаж, распознаваемая импортёром. При изменённых заголовках предусмотрено ручное сопоставление колонок. Новые клиенты и SKU требуют проверки справочников.

При повторном импорте строки продаж за совпадающие год и месяц заменяют предыдущую загрузку этого периода. План заменяется по году и месяцу. Это замена периода целиком: частичную выгрузку одной сети нельзя использовать как добавление к уже загруженному месяцу.

Источник факта в предоставленном формате — `Лист1`. Сводный `Лист2` и промежуточные итоги не добавляются к строкам продаж. План читается с листа `СВОД` по колонке `Категория А`; при необходимости колонку можно указать вручную. В примерах эта колонка имеет зелёную заливку.

## Методика расчётов

- Основное сравнение — 2026 к 2025; 2024 используется как история. По умолчанию выбирается период от января до последнего месяца в данных 2026. Месяцы выбранного периода одинаковы для каждого года.
- Выручка берётся из `Сумма отгрузки, с НДС, тенге`. Тоннаж рассчитывается из веса в кг, делённого на 1000. Отрицательные корректировки и возвраты сохраняются. Неизвестный вес помечается предупреждением и не восстанавливается из выручки.
- Прирост: `(факт 2026 − факт 2025) / факт 2025 × 100`. При нулевой базе процент не вычисляется; положительный текущий факт отмечается как новый.
- Доля: продажи сущности / все продажи того же периода и с теми же фильтрами. Изменение доли — разница долей в **п.п.**, прирост продаж — в **%**. По умолчанию потери ранжируются по сумме снижения в деньгах.
- Активность точки и SKU требует положительной отгрузки в деньгах или объёме. В исходных выгрузках нет устойчивого идентификатора торговой точки, поэтому АКБ определяется приближённо по сочетанию города и названия клиента.
- Сопоставимая база включает сети **и** дистрибуторов, активных в обоих сравниваемых периодах. Полная база сохраняет вклад новых и ушедших участников.
- Отсутствие строк за месяц может означать как отсутствие продаж, так и неполную выгрузку. Само по себе оно не подтверждает отключение клиента или дистрибутора.

### Особенности плана

План категории А в предоставленном формате задан в кг и показывается в тоннах. Денежный план отсутствует. Расчёт использует конечные строки городов и отдельные строки сетей, без добавления региональных подытогов. Сумма строк сверяется с контрольным итогом листа.

План сопоставляется с фактом того же месяца и доступного набора измерений. Если фильтр выделяет часть, на которую план не распределён, такое сравнение не выполняется. В сводном итоге месяца каждая строка факта учитывается один раз, в том числе при пересечении городского и сетевого плана.

В источниках есть объединённые группы `Макаронные изделия` (КМИ и Жайма), регион `Павлодар+Экибастуз` и отдельный план Small без полного распределения по городам. Интерфейс показывает ограничения сопоставления; факты отдельных строк с пересекающимся охватом нельзя складывать вручную.

Реалистичность определяется превышением заложенного роста над историческим ростом 2025/2024. По умолчанию до 10 п.п. — реалистичный план, свыше 10 до 25 п.п. — напряжённый, свыше 25 п.п. — нереалистичный. Рост плана при отрицательном тренде 2026/2025 за YTD также отмечается как нереалистичный. Пороги настраиваются.

Предоставленные CRM-файлы содержат месяцы, а не даты отгрузок. По ним нельзя подтвердить закрытие последнего месяца или получить достоверный среднедневной прогноз. План-факт следует читать с учётом этого ограничения.

## Локальный запуск

Нужны Node.js и npm; для совпадения с контейнером используйте Node.js 24. Версии зависимостей закреплены в `package-lock.json`.

```powershell
git clone https://github.com/MelNikVl/dbprodazh.git
cd dbprodazh
npm ci
$env:CRM_SAMPLE_DIR='D:/CRM'
npm run dev
```

Откройте [localhost:8050](http://localhost:8050). Сервер разработки слушает `127.0.0.1`, порт `8050` фиксирован. `CRM_SAMPLE_DIR` должен указывать на ваш каталог исходников; встроенный путь для исходного рабочего окружения можно переопределить этой переменной.

Для просмотра производственной сборки:

```powershell
npm run build
npm run preview
```

`dev` и `preview` используют один порт, поэтому одновременно запускается только один из них.

## Docker на домашнем сервере

Целевая схема каталогов:

```text
/home/nik/apps/dbprodazh/
├── app/     # этот репозиторий, compose.yaml и локальный .env
└── data/    # приватные исходные Excel, вне репозитория
```

На сервере нужны Docker Engine и Docker Compose v2+. Текущая установка передаётся архивом кода, без каталога `.git`; её обновление описано в [инструкции обслуживания](deploy/README.md#обновление-кода-и-исходников). Для нового развёртывания также можно клонировать репозиторий:

```sh
ssh nik@192.168.0.15
mkdir -p ~/apps/dbprodazh/data
cd ~/apps/dbprodazh
git clone https://github.com/MelNikVl/dbprodazh.git app
cd app
cp deploy/.env.example .env
docker compose up -d --build --wait
docker compose ps
curl --fail http://192.168.0.15:8050/health
```

Пример `.env` соответствует этому размещению:

```dotenv
BIND_ADDRESS=192.168.0.15
PUBLIC_ORIGIN=http://192.168.0.15:8050
CRM_SAMPLE_DIR=/home/nik/apps/dbprodazh/data
```

Исходные Excel копируются отдельно в `data/`. Контейнер работает от UID/GID `1000:1000`: ему нужны чтение файлов и доступ к каталогу. Образ содержит код и сборку приложения; каталог `/data` подключён только для чтения.

`BIND_ADDRESS` выбирает интерфейс сервера, `PUBLIC_ORIGIN` — точный адрес приложения. Без локального `.env` публикация порта ограничена `127.0.0.1`, путь данных — `../data`. Развёртывание рассчитано на доверенную домашнюю сеть: пользователь с доступом к адресу приложения может читать исходные Excel. Авторизация пользователей не реализована.

Обновление, логи, резервное копирование и диагностика описаны в [deploy/README.md](deploy/README.md).

## Проверки

```powershell
npm test
node --test server/routes.check.mjs
npm run build
```

Тесты аналитики и импортёра проверяют расчёты и обработку входных форматов на тестовых данных. Отдельные проверки HTTP-сервера охватывают маршруты, доступ к разрешённым файлам и ограничения запросов. Эти команды не заменяют проверку отчётов на актуальной выгрузке.

Сверка с приватными исходными файлами запускается отдельно. Ей нужен приватный файл контрольных значений `.local/reconciliation-controls.json`; другой путь задаётся через `CRM_CONTROLS_FILE`. Формат контрольного файла задаёт [тест сверки](src/reconciliation.test.ts). Контрольные значения должны быть получены независимым расчётом по тем же исходникам и не публикуются в репозитории.

```powershell
$env:CRM_SAMPLE_DIR='D:/CRM'
$env:CRM_RECONCILE='1'
$env:CRM_CONTROLS_FILE='.local/reconciliation-controls.json'
npm test -- --run src/reconciliation.test.ts
Remove-Item Env:CRM_RECONCILE
Remove-Item Env:CRM_CONTROLS_FILE
```

Отсутствие приватной сверки или исходных файлов не является подтверждением совпадения с учётной системой. Результат сверки относится к конкретным версиям файлов, использованным при её запуске.
